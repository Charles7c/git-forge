# Provider contract

The table describes what **git-forge** sends and returns, not every feature a host offers. API references: [GitHub REST](https://docs.github.com/en/rest), [Gitee API v5 Swagger](https://gitee.com/api/v5/swagger), [AtomGit OpenAPI](https://api.atomgit.com/.well-known/openapi.json). The [tool-name comparison](../README.md#how-the-23-tools-compare-to-github-mcp) is about MCP, not REST endpoints.

| Adapter | API base                         | Transport and identifiers                                                                                                                                                                                              |
| ------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GitHub  | `https://api.github.com`         | Bearer header; Issue numbers returned as strings, PR numbers as numbers. Issue listing removes PR entries.                                                                                                             |
| Gitee   | `https://gitee.com/api/v5`       | Bearer header; alphanumeric Issue numbers are preserved (e.g. `IEXA01`). Repository web URLs drop a trailing `.git`.                                                                                                   |
| AtomGit | `https://api.atomgit.com/api/v5` | Bearer header in the SDK, not a query token. Repository links prefer `web_url` when `html_url` is absent; identity uses namespace path, not the display name. The response's API `url` is not the next request target. |

## Differences that affect callers

| Operation           | SDK behavior (adapter contract, tested with synthetic responses)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Issue states/labels | Gitee `open`/`progressing` → `open`, `closed`/`rejected` → `closed`. Each normalized filter queries its two native states, then deduplicates; `all` uses one stream. Object labels become names. Gitee rejects a numeric Issue milestone filter locally (`INVALID_ARGUMENT`): its endpoint takes a milestone title. AtomGit accepts comma-separated labels in applicable query/write fields and uses `milestone` for issues vs `milestone_number` for PRs.                                                                                                                                                                                                                                                                           |
| IDs and links       | `Issue.number` retains the original text; the optional numeric alias is only for safe decimal integers. PR numbers are numeric. Comments on Gitee/AtomGit need not include a URL; expose the upstream URL or available parent link, otherwise omit it. Branch links are derived from the web base rather than obtained with a second request.                                                                                                                                                                                                                                                                                                                                                                                        |
| Pull requests       | `merged` is represented as `state: 'closed', merged: true`. AtomGit rejects a PR list `head` filter; no unfiltered substitution. A detail without a head may consult the list; if still unknown, `head` is absent. PR comments are conversation comments, not review threads.                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Reading files       | `getFileContents` requires a file path. Although Gitee/AtomGit describe a contents endpoint with an optional path, the SDK does not list directories. Arrays (including Gitee's empty array for some missing paths/refs) produce `INVALID_ARGUMENT`; an upstream 404 produces `NOT_FOUND`.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Writing files       | All three support single-file create/update/delete. SDK and MCP default to UTF-8; pass `encoding: "base64"` for pre-encoded bytes. The SDK derives Gitee's single-file commit URL when the response lacks it. `pushFiles` requires a nonempty list and returns one commit. GitHub checks the complete parent tree once for existence and regular-file modes before creating a tree/commit and updating the ref without force (6 requests plus 1 per base64 blob). Truncated trees and non-regular targets are refused. Gitee sends `POST /repos/{owner}/{repo}/commits` with ordered input actions (`create`, `update`, `delete`; no upsert); `utf8` becomes `text`, `base64` stays `base64`. The result's paths follow input order. |
| Unsupported writes  | The AtomGit adapter has no atomic multi-file implementation in the referenced API. It rejects `pushFiles` locally; it does not create a sequence of single-file commits.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Pagination          | Read the next-page signal from a Link header, total-page header or page size, subject to `maxPages`. The SDK constructs requests against the configured API base; web links are display data.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

## Verification boundary

| Covered locally                                                                                                                                                                                                                                             | Not established by these tests                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mock contracts check request formatting, mapping, supported/unsupported calls and error handling. Loopback HTTP exercises repository, issue, branch and commit reads through all three adapters. The stdio check exercises MCP discovery and call handling. | Live hosted reads/writes, token scopes, enterprise deployments, effective server-side filters, current quotas, merge policies and deployed API versions. An adapter accepting a field is not proof that a hosted API honors it. |
