# Provider contract

The table describes what **git-forge** sends and returns, not every feature a host offers. API references: [GitHub REST](https://docs.github.com/en/rest), [Gitee API v5 Swagger](https://gitee.com/api/v5/swagger), [AtomGit OpenAPI](https://api.atomgit.com/.well-known/openapi.json). The [tool-name comparison](../README.md#how-the-23-tools-compare-to-github-mcp) is about MCP, not REST endpoints.

| Adapter | API base                         | Transport and identifiers                                                                                                                                                                                              |
| ------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GitHub  | `https://api.github.com`         | Bearer header; Issue numbers returned as strings, PR numbers as numbers. Issue listing removes PR entries.                                                                                                             |
| Gitee   | `https://gitee.com/api/v5`       | Bearer header; alphanumeric Issue numbers are preserved (e.g. `IEXA01`). Repository web URLs drop a trailing `.git`.                                                                                                   |
| AtomGit | `https://api.atomgit.com/api/v5` | Bearer header in the SDK, not a query token. Repository links prefer `web_url` when `html_url` is absent; identity uses namespace path, not the display name. The response's API `url` is not the next request target. |

## Differences that affect callers

| Operation           | SDK behavior (adapter contract, tested with synthetic responses)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Issue states/labels | Gitee `open`/`progressing` → `open`, `closed`/`rejected` → `closed`; the raw value is preserved in `native_state` and the platform's own workflow title (`issue_state_detail.title`) in `state_label`. GitHub's `state_reason` is exposed when present and omitted when `null` — GitHub sends `null` on issues closed before the field existed. Each normalized filter queries its two native states, then deduplicates; `all` uses one stream. Object labels become names. Gitee rejects a numeric Issue milestone filter locally (`INVALID_ARGUMENT`): its endpoint takes a milestone title. AtomGit accepts comma-separated labels in applicable query/write fields and uses `milestone` for issues vs `milestone_number` for PRs. AtomGit's `issue_state` is a workflow label, not a state signal: measured issues with `state: 'closed'` still report `待办的`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Issue visibility    | `Issue.restricted` is set only where the platform marks an issue non-public: Gitee `security_hole` and AtomGit `visibility_reason` (`confidential` / `other`). GitHub exposes no per-issue marker, so the field is absent there — absence means "no signal", never "public".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Label events        | GitHub reads `issues/{n}/timeline`, keeps only `labeled` / `unlabeled` (the endpoint mixes dozens of event kinds) and deduplicates **only by each event's native `id`** — an entry without one is never merged with another, because a `(event, time, label)` tuple cannot distinguish `labeled` → `unlabeled` → `labeled` inside one second and collapsing those inverts the resulting state; repeating an id-less entry is preferred to dropping a real mutation. Gitee reads `repos/{owner}/issues/{n}/operate_logs?repo=` and maps `add_label` / `remove_label`, taking the name from `after_change_value` / `before_change_value` rather than the localized sentence. AtomGit reads the same owner-scoped path and parses names out of the English sentence (`add label a, b`), expanding one entry into one event per label; an unparseable sentence still reports the event, with `type: 'unknown'` and no `label`, rather than being recorded as an addition. **Neither Gitee's nor AtomGit's log accepts a `page` parameter**, so those two answer in a single request and `maxPages` does not apply. All three return **oldest-first**, sorted after retrieval by parsing each timestamp (so `+08:00` and `Z` spellings of one moment compare equal); the sort is stable, and an unparseable timestamp stays last in its original relative position. |
| IDs and links       | `Issue.number` retains the original text; the optional numeric alias is only for safe decimal integers. PR numbers are numeric. Comments on Gitee/AtomGit need not include a URL; expose the upstream URL or available parent link, otherwise omit it. Branch links are derived from the web base rather than obtained with a second request.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Pull requests       | `merged` is represented as `state: 'closed', merged: true`. Gitee queries `closed` and `merged`; AtomGit also queries `locked`. Each native stream has its own `maxPages` budget, then results are deduplicated. GitHub filters the received rows by all requested label names and milestone number. A missing required `base` produces a provider error unless recoverable from the same PR. AtomGit rejects a PR list `head` filter; no unfiltered substitution. PR numbers must be positive safe integers; details must match the requested number. Only a same-number row can supply missing refs. Unknown `head` remains absent. PR comments are conversation comments, not review threads.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Reading files       | `getFileContents` requires a file path. Although Gitee/AtomGit describe a contents endpoint with an optional path, the SDK does not list directories. Arrays (including Gitee's empty array for some missing paths/refs) produce `INVALID_ARGUMENT`; an upstream 404 produces `NOT_FOUND`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Visibility          | `Repository.visibility` is derived from the strongest statement the payload makes: GitHub's `visibility` word (`public` / `private` / `internal`), then an `internal` flag, then an explicit `public: true`, then either private signal (AtomGit declares those flags as integers in several schemas and sends booleans live, so both are accepted). **A bare `private: false` is not public evidence**: GitHub Enterprise `internal` repositories report it too, and so does a payload that omits visibility entirely, so that input answers `unknown`. `private` stays a boolean for compatibility and is `true` for `internal`, but only `visibility` distinguishes "not private" from "not stated".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Stars               | `Repository.stargazers_count` is present on all three platforms and omitted when the payload has no count. `listStargazers` is supported on GitHub and AtomGit; GitHub reports `starred_at` only under the `application/vnd.github.star+json` media type, which the `timestamps` parameter selects, and its endpoint requires authentication. **Gitee's `/stargazers` is routable but answers `[]` for every repository measured**, including large ones and with a token, so the capability is declared unsupported rather than returning a misleading empty list.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Releases            | Only GitHub sends `published_at`, `html_url` and `draft`. Gitee and AtomGit send `created_at` and nothing else, so that value is reported as `published_at` with the caveat documented on the model. No release URL is derived for them: Gitee's `/releases/tag/<tag>` answers a 302 to a source archive for a non-client browser user agent, so a guessed link would point at the wrong page. Both are queried with `direction=desc`, and the **retrieved** entries are then sorted newest-first locally, because upstream order is not reliable once pagination is merged (a measured page set returned a November release after a February one). Entries with no timestamp sort last and keep their relative order. AtomGit's `release_status` names both directions: `pre` → `pre_release: true`, `latest` (spelled `lasted` in one schema) → `false`, anything else stays unknown.                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Commits and authors | `listCommits` accepts `since` / `until` and forwards both; all three platforms filter server-side (verified: an out-of-range window returns `[]`). Both bounds must carry an explicit zone (with an hour ≤ 23 **and** a minute ≤ 59 — `+00:60` is refused, since checking the combined total would accept it), name a real calendar date (`2026-02-30` is refused rather than rolled into March), and an inverted window is refused at the nine fractional digits ISO 8601 allows — anything coarser compares equal and lets a sub-millisecond inversion through. Years below 100 are handled without the two-digit-year rule, so `0099` is the first century, not 1999. `Commit.author.user` is filled from the **author** side only; the committer is frequently `web-flow` or a bot. The account requires a real `login` and is never synthesised from a display name **or an email**. The author block is produced from any one of the Git-side name, email or date, so an email-only commit keeps its email rather than losing it; that email is never copied over from the platform account, and an unstated field stays an empty string. The link is often absent: measured on one repository, Gitee returned a `null` author for 12 of 20 commits and AtomGit omitted `commit.author.name` for 11 of 30.                                               |
| Labels              | `listLabels` / `createLabel` / `ensureLabel`. `color` is normalized to `#rrggbb` on read; on write the `#` is stripped for GitHub and Gitee (both want six bare hex digits) and kept for AtomGit. Create bodies differ: GitHub takes JSON, Gitee and AtomGit take form-encoded `name` + `color` (both required by the platform). Gitee's own Swagger is self-contradictory here — it declares `consumes: application/json` while listing `name`/`color` as `formData` — so the form encoding follows the parameter list and is pinned by a test rather than asserted as the only reading. **Neither Gitee's nor AtomGit's label write accepts a description** (their create body is `name` + `color` only), so a description is dropped on both instead of being reinterpreted. `listLabels` accepts `requireComplete`, which also validates the response shape; see below.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Ensure-exists       | `ensureLabel` reads with `requireComplete: true` and refuses with `PAGINATION_LIMIT` when the page budget truncated the listing, because a truncated list is indistinguishable from "the name is absent" and acting on that reading would create a duplicate or mask the truncation. The same read rejects a malformed catalog (non-array body, row with no usable `name`) with `PROVIDER_ERROR`. Either way the create path is never reached, so no POST is issued. Name matching is case-insensitive. `color` is optional and becomes required only once a create is actually issued. It is still not a conditional create: two concurrent callers can race, and the loser re-reads once before the upstream error is reported.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Writing files       | All three support single-file create/update/delete. SDK and MCP default to UTF-8; pass `encoding: "base64"` for pre-encoded bytes. The SDK derives Gitee's single-file commit URL when the response lacks it. `pushFiles` requires a nonempty list and returns one commit. GitHub checks the complete parent tree once for existence and regular-file modes before creating a tree/commit and updating the ref without force (6 requests plus 1 per base64 blob). Truncated trees and non-regular targets are refused. Gitee sends `POST /repos/{owner}/{repo}/commits` with ordered input actions (`create`, `update`, `delete`; no upsert); `utf8` becomes `text`, `base64` stays `base64`. The result's paths follow input order.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Unsupported writes  | The AtomGit adapter has no atomic multi-file implementation in the referenced API. It rejects `pushFiles` locally; it does not create a sequence of single-file commits.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Pagination          | Read the next-page signal from a Link header, total-page header or page size, subject to `maxPages`. The SDK constructs requests against the configured API base; web links are display data.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

For SDK `listIssues`, each fetched page must be an array. Issue rows must have a native `number` (nonblank string or finite number) and a recognized `state`: `open` or `closed`, plus `progressing` and `rejected` on Gitee. GitHub PR rows count toward page size but are not validated as Issues or returned. A malformed page or Issue row rejects with `PROVIDER_ERROR` (including provider, HTTP status and request ID when available), even after earlier pages succeeded.

With `requireComplete: true`, `listIssues` honors `Link` next-page hints, a valid `total_page` / `x-total-pages`, and recognized terminal pagination links. A full page without a usable hint probes the next page when budget permits; at the cap it conservatively rejects with `PAGINATION_LIMIT`. Gitee applies the cap to each native state stream and rejects the whole call if any stream hits the cap with more data indicated. This flag does not guarantee a consistent snapshot or detect all missing provider hints. Other list methods and MCP do not opt in, except `listLabels`.

With `requireComplete: true`, `listLabels` additionally rejects a page body that is not an array, and a row whose `name` is missing, blank or not a string, with `PROVIDER_ERROR` naming the offending shape. Both would otherwise be read by the mapper as a short list and become "the name is absent", which is the premise `ensureLabel` acts on. Without the flag (`git_list_labels`, and any direct `listLabels` call) the lenient reading is unchanged: a non-array body yields `[]` and an odd row is mapped as far as it can be.

`ensureLabel` always reads with `requireComplete: true`, so a malformed or truncated catalog never reaches the create path. A valid empty array with a colour supplied does create; a shape or budget failure does not, and issues no POST.

## Verification boundary

| Covered locally                                                                                                                                                                                                                                             | Not established by these tests                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Mock contracts check request formatting, mapping, supported/unsupported calls and error handling. Loopback HTTP exercises repository, issue, branch and commit reads through all three adapters.
